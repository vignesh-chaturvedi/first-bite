Who it serves and how we measure success

Newcomer: owns a wallet and an invitation, lacks COOK, and wants an identity usable across Cookie apps. Operator: runs one finite campaign, issues wallet-bound passes and pays known costs. There is no open sponsor marketplace in this release.

The first release is successful when five real pilot users can complete the journey without manual funding, ownership and primary-name reads are correct, at least one independent ecosystem tool resolves their names, and accounting reconciles every sponsor debit. These are proposed acceptance targets, not usage already achieved.

MVP scope

  • Nightly connection and explicit Cookie network guidance.
  • Private, single-use, wallet-bound invitations.
  • Available names: 4–32 ASCII characters, using the registry's rules.
  • Live quote, a bounded sponsored transaction and durable status tracking.
  • Completion page with ownership proof and an existing-tool handoff.
  • Operator CLI for campaign setup, invitations, pause and reconciliation.

After the bounty

Multiple campaigns, a self-service sponsor dashboard, a reusable SDK, additional sponsored actions, Kora integration and external analytics may follow demonstrated adoption.

Version one contains no new naming program, NFT badge, token, bridge, swap, arbitrary transaction relay, public faucet, AI chat or webhook platform. Do not add these to fill time.

03 / What runs where

One product, three deployed services

  1. Browser + NightlyReads campaign status, chooses a name, displays an exact review and produces the user's signature. Never holds a sponsor key.
  2. Next.js web/APIValidates invitations, quotes costs, reserves budget, constructs fixed transactions, validates signatures and persists the signed payload before broadcasting.
  3. PostgreSQLAuthoritative campaign ledger, access capabilities, current state, signing attempts and durable reconciliation jobs.
  4. Reconciliation workerContinues after tab closure. Checks transaction history, finality, current ownership and account balances. Cannot create a replacement registration while the old one is unresolved.
  5. Cookie RPC + registryExecutes the approved transaction against the existing registry. Chain state is authoritative for funds, name ownership and primary identity.
  6. Existing ecosystem toolIndependently resolves the user's new name. First integration target: CookBook or a verified name-capable Cookie tool.

On-chain responsibility

Transfer the exact sponsor allocation; register a fresh name; move ownership to the user; establish their primary record. The registry enforces uniqueness and owner signatures. No new Anchor program is planned.

Off-chain responsibility

Campaign eligibility, invite issuance, budget policy, quotes, signing policy, transaction history and operator controls. These controls depend on the service and its keys; the campaign cap is not a decentralized on-chain guarantee.

Trust boundaries: the user keeps their wallet keys; the operator controls sponsorship keys; the existing registry retains its upgrade/admin trust model; RPC availability affects status verification. A bounded hot-wallet balance limits damage if the service is compromised, but application policy cannot protect funds from a stolen sponsor key.

04 / The implementation sequence

Nine phases, each with an exit gate

Complete the output and prove the gate before moving on. UI preparation can overlap with backend work once Phase 0 locks the transaction contract. Gates involving funds require an explicitly agreed test amount; this planning document does not fund or send anything.

00Prove the transaction and fundable pilotDay 1 · 6–8 hours · Dependency: none · Hard stop before implementation

Resolve the two unknowns that could invalidate the app: wallet compatibility and the cost/ownership behavior of the existing registry.

Work

  • Re-read the official listing, registry config, program/IDL revision, account layouts, current name prices and RPC genesis identity. Save observations and dates.
  • Verify Nightly can select Cookie, sign the candidate three-signer transaction, and preserve its message. Connection, signing, simulation and broadcast are separate checks.
  • Prove the bounded-payer transaction described below: fund attempt payer → register → transfer name → fund primary-account rent → set primary. Check byte size, rent, compute and final account ownership.
  • Exercise price-change and invalid-name behavior in a controlled fixture/local validator when possible. Do not alter the live registry. Use one approved live registration for the real-wallet smoke test.
  • Confirm exact primary-record arguments against the IDL. The inspected set_primary_domain instruction has no name argument; it receives the domain account.
  • Choose a finite pilot allocation and a distribution path. Proposed start: ten eligible wallets, one pass each, at least five observed newcomers.
Outputs: docs/feasibility.md, pinned IDL/source reference, actual transaction signature, ownership/primary readback, tested dependency versions, cost worksheet and chosen campaign cap.

Exit gate

A zero-COOK Nightly user becomes final owner with a matching primary record; the user's wallet is never the payer for variable registration price; instructions fit a supported transaction; sponsor costs are bounded; the pilot has an owner and budget. Unexplained signing warnings or unbounded debits fail this gate. Revise the design rather than quietly weakening it.

Leave unchecked until the evidence exists. This document has not run the proof.

01Create the application foundationDay 2, first half · 3–4 hours · Dependency: Phase 0

Create a predictable workspace and a deployable empty shell before adding sponsorship logic.

Work

  • Initialize Next.js, strict TypeScript, pnpm, Tailwind and the small component set. Pin Node/dependency versions from Phase 0.
  • Create shared configuration validation, server-only imports, typed API errors, a structured logger and an initial route layout.
  • Set up local PostgreSQL, Drizzle migrations, deterministic non-secret fixtures and separate development/test environments.
  • Add CI for type checking, lint, targeted tests and production build. Include a secrets exclusion policy and license/attribution notes.
  • Configure an unfunded deployment shell, health endpoints and a worker entry point. Validate build/start and graceful shutdown.
Outputs: repository skeleton, lockfile, .env.example, initial migration, CI workflow, theme tokens and an unfunded preview.

Exit gate

A fresh checkout can install, migrate, run and build using documented commands. CI is green. No real signing key appears in source, browser bundles, logs or test fixtures.

02Build the registry client and transaction engineDay 2, second half → Day 3 · 5–6 hours · Dependency: Phases 0–1

Turn the validated proof into a small deterministic module with explicit cost and authority boundaries.

Work

  • Implement normalization, availability, config decoding, domain and primary PDA derivation, and live rent/fee reads.
  • Use BigInt native units and decimal strings at JSON boundaries. Reject malformed, taken, short-tier and over-32-byte names before preparing transactions.
  • Implement the fixed instruction sequence, exact expected account metas, recipient, fee receiver and program IDs. Treat any upstream change as a review event.
  • Quote a maximum sponsor debit; assign one fresh attempt payer; record the message hash, blockhash, last valid block height and expected final state.
  • Implement a decoder/validator independent enough to reject message tampering. Test literal expected instruction/account data, not merely a round trip through the same builder.
Outputs: src/lib/chain/, src/lib/transactions/, fixed-action policy, quote type and encoding/pricing tests.

Exit gate

Given the same inputs, the engine produces the expected instructions and maximum debit. Changed accounts, instruction order, amounts, compute limits or name data are rejected. Variable name registration cannot charge the user's other funds.

03Implement invitations and budget accountingDay 3 → Day 4 · 5–6 hours · Dependency: Phases 1–2

Make it impossible for normal concurrent requests to spend the same invitation or reserve the same campaign capacity twice.

Work

  • Add the campaign, invite, quote, attempt and append-only ledger tables with the constraints defined below.
  • Issue random invitation tokens through the operator CLI, store only token hashes, bind each to an expected wallet and set campaign/expiry limits.
  • Exchange a token for a short-lived HttpOnly capability session. A capability permits preparing that invite's action; it is not proof of wallet ownership. Only the valid transaction signature authorizes spending.
  • Reserve invitation, name and worst-case spend in a database transaction. Lock the campaign row for its cap; use unique active-attempt constraints and idempotency keys.
  • Implement prepared-but-unsigned expiration. Once co-signing begins, use the stricter chain reconciliation rules; a wall-clock timer cannot release that budget.
  • Enforce limits per invitation, wallet/session and source IP, plus a global prepare/sign rate. Rate limiting supports a closed pilot; it is not proof of unique humans.
Outputs: migrations, invitation CLI, session exchange, reservation service, typed accounting events and concurrency tests.

Exit gate

Parallel requests against one invite or the last campaign slot produce at most one signable attempt. Available budget never becomes negative. Expired unsigned attempts release only their own reservation; signed/uncertain attempts retain theirs.

04Ship the signing service and recovery workerDay 4 → Day 5 · 6–8 hours · Dependency: Phases 2–3

Execute the approved action once and recover correctly from timeouts, tab closure and service restarts.

Work

  • Verify the submitted user signature and exact stored message, current invite/campaign state, quote validity, sponsor balance and current program/config policy.
  • Simulate before signing; fail closed if RPC, config or account state cannot be checked. Atomically claim the attempt for signing.
  • Co-sign with the sponsor and per-attempt payer. Persist full signed bytes, signature and a reconciliation job before broadcasting. Do not expose the sponsor or attempt secret to the browser.
  • Implement submitted, broadcast_unknown, confirmed, finalized, failed, expired and manual_review transitions.
  • Re-broadcast the identical transaction while valid. For a replacement, prove the old attempt cannot still succeed and require a new user approval.
  • After finalized success, read domain/primary records and transaction metadata, consume the invite, settle actual sponsor cost and account for any bounded-payer residual.
  • Keep failed transaction fees in the campaign ledger. Recover residual COOK only to the sponsor, through a separate constrained operation covered by a recovery budget.
Outputs: submit/status APIs, durable worker, signature-based reconciliation, signing-key lifecycle and operator recovery commands.

Exit gate

A crash after persistence, a lost send response and a closed browser all converge on the same signature and one settlement. Unknown status never becomes “failed” merely because time passed. Price increases cannot borrow registration funds from the user or main sponsor account through the registry.

05Complete the newcomer experienceDay 5 → Day 6 · 6–8 hours · Dependency: API contracts in Phase 3; final wiring after Phase 4

Make the product understandable without teaching the user about relayers, PDAs or account rent.

Work

  • Build invitation entry, wallet connection, name selection, review, progress and result screens as one coherent journey.
  • Show the connected address and network, sponsor coverage, name and owner before signing. Keep diagnostics in a details view, not in the main path.
  • Handle missing Nightly, wrong network/wallet, consumed or expired pass, already-owned name, unavailable name, budget exhausted, rejected signature, offline and RPC failure states.
  • Debounce availability checks and discard stale responses. An available result is a check, not an on-chain reservation.
  • Restore in-progress attempts after reload using the capability session and opaque attempt ID. Never store secrets or signed bearer transactions in localStorage.
  • Verify the result from on-chain reads; show confirmed separately from finalized. Link to the explorer and one existing name consumer, with no invented deep links.
Outputs: six product screens, reusable status components, responsive layout, accessible forms and a complete preview flow.

Exit gate

A newcomer can explain what they receive, who pays and what they approve. The real Nightly journey works on supported desktop browsers. At 375, 768 and 1280 pixels, controls remain usable and no critical content is clipped. Mobile signing is advertised only if separately tested.

  • Complete operator commands for pause/resume, invite issuance, revoke-before-sign, accounting export, attempt inspection and residual recovery.

05 / The most important implementation contract

Bound the sponsor payment before the registry can spend it

The existing registration instruction has a payer, but no separate final owner and no maximum-price argument. A direct top-up to the user followed by registration could let a changed registry price consume the user's other balance. The candidate below isolates the variable registration cost.

ActorAuthorityAllowed use
Sponsor STransaction fee payer and signerTwo explicit bounded transfers and fixed fee/compute policy. Never passed as registration payer.
Attempt payer AFresh, server-controlled signer for one attemptReceives only registration allocation, pays registry fee/rent and transfers the newly registered name to U. Starts with zero balance and no primary record.
User UNightly signer and final ownerAuthorizes the reviewed transaction and creation of their primary record. Does not pay the variable registration charge and never shares a secret.
  1. S → A: transfer the quoted registration price plus the current rent required for the domain account.
  2. Register: invoke the existing registry with A as payer; the new name initially belongs to A.
  3. Transfer ownership: A authorizes transfer of that name to U, using the plain transfer variant because A has no primary record.
  4. S → U: transfer only the exact additional rent required for creating U's primary record. If the required record already exists, verify policy and omit unnecessary funding.
  5. Set primary: U authorizes the existing instruction against the just-transferred domain and U's primary PDA.

These instructions, plus only the approved compute-budget instructions if necessary, must fit one atomic transaction signed by S, A and U. All ordinary instruction state changes roll back on failure; transaction fees may still be charged. The interim ownership is not a separately settled transfer. This composition passed local proof and one finalized live registration on 21 September 2026; campaign activation remains separate.

If the registry price rises

A holds only the quoted allocation. Registration must fail rather than draw the difference from U or S. Confirm this behavior with a changed-price fixture, including a user who already has other COOK.

If the registry price falls

A may retain sponsor-owned COOK, or the transaction may fail because of the resulting rent conditions. Reconcile actual state. Count the full allocation as spent until a verified recovery returns funds; never assume the residual was recovered.

Cost model and exact units

P = registration price from verified live registry config
D = getMinimumBalanceForRentExemption(149)  // domain layout: re-verify in Phase 0
R = required primary-account funding        // current layout 77 bytes; may already exist
F = getFeeForMessage(exactMessage)            // includes required signatures/priority policy
Q = separate maximum recovery-fee allowance

maximum reservation = P + D + R + F + Q
capacity available = campaign cap - settled debits - active reservations

COOK display = native base units / 1_000_000_000
Use BigInt arithmetic. JSON amounts are decimal strings, never floating point.

Research snapshot: long-tier registration was 15,000 COOK and short-tier was 35,000 COOK. Version one sponsors only 4–32-character names, so ten registrations would require 150,000 COOK plus the other terms at that snapshot. These are configurable protocol charges, not live dollar valuations. Saved RPC observation.

Recovery accounting: completing registration settles its actual debit but retains Q as an active recovery reservation. Release Q only after recovery finalizes or an operator explicitly abandons recovery with the residual recorded as spent and no unresolved signed sweep. Every additional recovery attempt needs its fee reserved under the campaign cap before signing. Count a refund only after verified finalization; never offset the original allocation with an expected return.

Signing and crash-safety sequence

  1. Validate invite/capability and expected wallet. Re-read config, name and account state. Allocate a fresh A and reserve the maximum cost under database locks.
  2. Generate the exact message with a recent blockhash. Save its bytes/hash, quote/config fingerprint, program identity, policy version, expiry block height and expected outcome. Return only the user-signable transaction.
  3. Nightly signs without changing the message. On return, compare exact message bytes, verify U's signature and all required identities. Revalidate policy and simulate the candidate; invalid signatures or extra instructions fail.
  4. Under the same campaign/invite locks used by pause and revocation, recheck their status, expiry and policy version, then atomically move prepared → signing. This committed transition is the authorization boundary: later pause/revocation blocks new transitions, but this attempt may finish signing and broadcast. Release locks before network work. Co-sign server-side. Save the fully signed payload, signature and work item durably before any send. If persistence fails, send nothing.
  5. Broadcast. A send timeout becomes broadcast_unknown; the worker inspects the same signature. It may re-send identical bytes, never silently refresh the blockhash on signed bytes.
  6. After finalized success, verify the resulting owner/primary, reconcile sponsor debit and receipt metadata, then consume the invitation. Inconsistency becomes manual_review with the budget held.

State and retry policy

quote → prepared → signing → signed → submitted / broadcast_unknown
                                           ↓
                                        confirmed
                                           ↓
                                finalized + verified → complete

finalized failure / proven expiry → settle fees → release unused execution reservation
unavailable or conflicting history → manual_review → keep reservation

Only an unsigned preparation can expire by a short wall-clock lease. A definitive on-chain failure means a finalized transaction with an error; a confirmed error remains provisional. A provably unsigned, never-broadcast rejection can terminate without chain execution. After co-signing, use transaction history and finalized block-height validity; “no result” is not proof of failure. A transaction can have landed before its blockhash expired. Rebuild only after the old attempt is conclusively failed or expired without landing, then obtain a fresh user signature. An ownership lookup alone cannot prove this app paid for the registration. Confirmation reference.

Key lifecycle: generate A on the server, encrypt its secret with authenticated encryption and an environment-provided wrapping key, bind ciphertext to the attempt ID, and keep it out of logs. The worker may use A only for already-approved signatures or recovery to S. Delete its recoverable secret after terminal reconciliation and residual settlement; retain public audit metadata. S is a dedicated, minimally funded hot wallet, separate from the operator's treasury.

Invitation handling: distribute a high-entropy code, optionally in a URL fragment consumed by the client and immediately removed from browser history. Operator runbook requirements

  • Pause: commit paused status under the same campaign lock as entry into signing. Block all subsequent signing transitions; show the operator attempts that already crossed that boundary and may still sign/broadcast. Continue reconciliation. Revocation has the same boundary; neither action cancels an already authorized attempt.
  • Monitor: campaign available/reserved/spent, actual sponsor balance, aged pending attempts, manual reviews, worker heartbeat, RPC health, residual balances and unexpected program/config changes.
  • Recovery: inspect signature/history; re-broadcast only stored valid bytes; settle only proven outcomes. Escalate unverifiable cases for manual review with reservations retained.
  • Key incident: pause, stop new signing, isolate affected keys and account for outstanding signed transactions. A leaked sponsor key can spend its funded balance, so keep the treasury elsewhere.
  • Release/rollback: one migration step before compatible app/worker deployment; preserve old attempts and decryption capability. Rollback must not erase the ledger or reset pending state.
  • Retention: delete consumed/expired invite secrets and terminal attempt secrets according to the documented policy; retain transaction IDs and aggregate pilot evidence needed to explain the campaign. Wallet identities are public on-chain but should not be needlessly published as participant lists.
