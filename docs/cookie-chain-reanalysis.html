03 / The build I would test first

First Bite: a name you can use, without a bridge detour

The user is a newcomer invited by a Cookie builder or community campaign. The job is to get a recognizable identity on Cookie Chain without first buying COOK and navigating a bridge. The organizer purchases a finite set of onboarding completions. This is a campaign service using the existing naming system.

  1. 01 · Open an inviteSee what the sponsor covers and connect Nightly on Cookie Chain.
  2. 02 · Pick a nameCheck availability; limit the campaign to eligible names of four or more characters.
  3. 03 · Review and signShow ownership, the real registration price, sponsor contribution, and resulting primary name.
  4. 04 · Use the resultRead ownership back from the chain and demonstrate resolution through an existing ecosystem tool.
Include in version one
  • One campaign; wallet-bound, single-use invitations; a fixed total spend ceiling.
  • Live name availability and registration cost.
  • Sponsored registration and primary-name setup.
  • Clear wallet/network, rejection, taken-name, expired-blockhash and pending states.
  • Independent ownership verification, transaction link, and a simple completion counter.
Keep outside the submission scope
  • A competing name registry or marketplace.
  • Compressed NFT badges and “first-ever” claims.
  • A full SDK, general-purpose relayer, or webhook service.
  • Permissionless free claims with only wallet rate limits.
  • AI chat, token issuance, price feeds, and a new bridge.

Why this has a case, and why it could still lose

There are two concrete indications of the problem: the official onboarding path sends users to acquire COOK through bridging, and Crumbs' usage instructions also require obtaining COOK before acting. Those support a friction hypothesis. The ecosystem registry and the sponsor's name integration establish that a registered name has existing consumers.

None of those proves demand for subsidized names. CookBook already registers names, Cookie Tin already sponsors actions, and fee abstraction already exists on Solana through Kora. Your defensible difference for this bounty must be a noticeably easier end-to-end journey and a real group using it. Without those, it risks looking like a sponsored reskin.

The cost that changes the scope

A read-only RPC check at slot 24,865,300 returned the name registry configuration: four-or-more-character registration costs 15,000 COOK; one-to-three-character names cost 35,000 COOK. The program's configured reference price is 100 micro-dollars per COOK, with tier settings of 150 and 350 cents. These are contract parameters, not a live market-price quote.

At that configuration, ten long-name registrations require 150,000 COOK plus rent and network fees. Registration is the dominant cost; “gas is almost free” is the wrong budget argument. Start with a strictly capped pilot, and decide its spend ceiling before funding. The program can change its configuration, so re-read the quote before constructing each action. Raw RPC evidence · Pricing code.

Integration first; no custom program required

The inspected instruction builders have a registration payer and an owner who pays for primary-name creation. Simply changing the transaction fee payer will not cover those costs. The candidate composition is a precisely bounded sponsor top-up to the user, registration by the user, and primary-name setup in one atomic transaction. Both parties sign the same bytes; registration failure should roll back the top-up, although network fees can still be charged. This composition remains to be transaction-tested with Nightly.

The backend should construct only that fixed action, verify returned bytes and the user signature, reserve one invitation and its budget, co-sign, and reconcile by transaction signature. It must bound fees, rent, recipient, registry, name and price, with no arbitrary user-supplied instructions. Keep pending distinct from failed; do not re-create an action merely because confirmation timed out. Reuse existing instruction code with its license and attribution. Kora is an optional signing component if a quick compatibility check succeeds, not a prerequisite.

Blockchain necessity: this app's benefit is ownership in the existing on-chain naming registry and use by other Cookie tools. Campaign eligibility and analytics can stay off-chain. A badge or database username alone would not provide that interoperability.

05 / If the first choice fails its gate

Bridge Check: help a user finish a transfer safely

A concrete alternative is a companion around the existing Hyperlane route. Connect Nightly, verify the selected route and recipient, check funds and destination requirements, initiate an explicitly reviewed transfer through the existing integration, then show source confirmation, message delivery, and destination receipt separately.

The sponsor's changelog documents destination-collateral preflight and warns that confirmation timeouts can be mistaken for failures. These are real failure modes, but some protections already exist in MCP. The bridge itself is already live. This idea succeeds only if its browser workflow handles a remaining observed problem better.

Limit the first version to one direction and the cases you can reproduce. It should say when a user must wait or contact the bridge operator. Do not promise to recover locked funds, replace the relayer, or safely retry an unknown transaction. Include a real, user-authorized on-chain operation so the app is more than a status viewer.

Why it is second: cross-chain states are harder to verify, some failures cannot be fixed by your app, and the existing bridge may already address the friction. Before switching, reproduce one gap in its current UI and prove the bridge/signing integration. Estimated implementation: five to seven focused days after that proof, with material uncertainty.
06 / What judges can actually inspect

Make the completed journey easy to verify

The brief requires Nightly support, a visible connected address, meaningful transactions, confirmation and errors, a public app, source, and setup instructions. Include applicable addresses and the requested X demonstration thread; share it in the Cookie community. Bridge guidance applies where relevant.

For First Bite, the demo should show a zero-balance wallet, an available name, an explicit sponsored action, a confirmed result, and the name resolving in another tool. Supply a limited invitation route for reviewers and an honest “campaign exhausted” state. Do not expose relayer keys or manufacture adoption numbers.

File the catalogue PR with screenshots and a clear description. It supplements the Superteam entry. A custom program, NFT, AI feature, and “first on chain” headline are not substitutes for this evidence.
